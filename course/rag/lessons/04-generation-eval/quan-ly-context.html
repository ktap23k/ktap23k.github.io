Quản lý context window và chi phí

Context window hàng trăm nghìn token không có nghĩa là nên dùng hết. Mỗi token thêm vào làm tăng tiền, tăng độ trễ, và quá một mức nào đó còn làm câu trả lời kém đi.

Mục tiêu bài học

  • Lập ngân sách token cho từng phần của prompt.
  • Chọn context đa dạng bằng MMR và đóng gói theo ngân sách.
  • Dùng prompt caching và biết khi nào long-context thay được RAG.

Ngân sách token

context window ≥ system prompt + lịch sử hội thoại + tài liệu + câu hỏi + chỗ cho câu trả lời

Hãy cố định ngân sách cho từng phần thay vì "còn bao nhiêu nhét bấy nhiêu". Ví dụ cho một chatbot nội bộ: system 1.000 token, lịch sử 2.000, tài liệu 6.000, câu trả lời 1.500. Khi lịch sử vượt ngân sách, tóm tắt các lượt cũ thay vì cắt bỏ.

Nhiều context hơn không phải lúc nào cũng tốt hơn

  • Chi phí tăng tuyến tính theo token đầu vào, nhân với số truy vấn mỗi ngày.
  • Độ trễ: thời gian tới token đầu tiên tăng theo độ dài prompt.
  • Chất lượng: nghiên cứu "Context Rot" của Chroma (2025) thử 18 model và thấy hiệu năng giảm khi input dài ra, kể cả với tác vụ đơn giản; cộng thêm hiện tượng lost in the middle ở bài trước.
  • Nhiễu: đoạn gần liên quan nhưng sai (quy định cũ, sản phẩm khác) dễ khiến model trả lời nhầm.

Đa dạng hoá context với MMR

Top-5 theo độ liên quan thường gồm năm đoạn gần giống nhau. Maximal Marginal Relevance chọn từng đoạn sao cho vừa liên quan tới câu hỏi, vừa khác các đoạn đã chọn: điểm = λ·liên_quan − (1−λ)·trùng_lặp_lớn_nhất.

import numpy as np

def mmr(query_vec: np.ndarray, doc_vecs: np.ndarray, k: int = 5, lam: float = 0.7) -> list[int]:
    relevance = doc_vecs @ query_vec
    selected: list[int] = []
    candidates = list(range(len(doc_vecs)))
    while candidates and len(selected) < k:
        redundancy = (doc_vecs[candidates] @ doc_vecs[selected].T).max(axis=1) \
            if selected else np.zeros(len(candidates))
        scores = lam * relevance[candidates] - (1 - lam) * redundancy
        best = candidates[int(np.argmax(scores))]
        selected.append(best)
        candidates.remove(best)
    return selected

def pack(chunks: list[str], budget: int, count_tokens) -> list[str]:
    """Lấy lần lượt các chunk (đã xếp theo độ liên quan) cho tới khi hết ngân sách token."""
    packed, used = [], 0
    for chunk in chunks:
        cost = count_tokens(chunk)
        if used + cost <= budget:
            packed.append(chunk)
            used += cost
    return packed

count_tokens nên dùng tokenizer của đúng model bạn gọi (hoặc API đếm token của nhà cung cấp); ước lượng theo số ký tự sai lệch đáng kể với tiếng Việt.

Nén context

  • Trích câu: giữ lại những câu trong chunk liên quan tới câu hỏi (dùng embedding hoặc reranker ở mức câu).
  • Loại token thừa: các phương pháp như LLMLingua dùng model nhỏ để bỏ token ít thông tin — tiết kiệm nhiều nhưng có thể làm mất chi tiết quan trọng.
  • Tóm tắt lịch sử: giữ nguyên văn vài lượt gần nhất, tóm tắt phần cũ hơn.

Prompt caching

Hầu hết nhà cung cấp LLM lớn đều hỗ trợ cache phần đầu prompt lặp lại giữa các request, giảm mạnh chi phí và độ trễ cho phần đó (Anthropic báo cáo giảm độ trễ hơn 2 lần và chi phí tới 90% trong trường hợp của Contextual Retrieval). Để tận dụng:

  1. Phần ổn định đặt trước: system prompt, định nghĩa tool, tài liệu tĩnh dùng chung.
  2. Phần thay đổi đặt sau: chunk vừa tìm được, câu hỏi.
  3. Đừng chèn thứ thay đổi liên tục (thời gian hiện tại, request id) vào đầu prompt — nó phá cache.

Khi nào long-context thay được RAG?

Nếu cả kho nhỏ (dưới khoảng 200.000 token) và ít thay đổi, đưa toàn bộ vào prompt kết hợp caching thường đơn giản và tốt hơn RAG. Hướng tiếp cận "Cache-Augmented Generation" (Chan và cộng sự, 2024) đẩy ý tưởng này xa hơn bằng cách tính sẵn KV-cache cho toàn bộ tri thức. Khi kho lớn, thay đổi thường xuyên, cần phân quyền theo người dùng hoặc cần dẫn nguồn chính xác — RAG vẫn là lựa chọn đúng.

Tóm tắt

  • Đặt ngân sách token cố định cho từng phần prompt.
  • Nhiều context hơn làm tăng chi phí, độ trễ và có thể giảm chất lượng.
  • MMR loại đoạn trùng lặp; đóng gói theo ngân sách bằng tokenizer thật.
  • Phần ổn định ở đầu prompt để tận dụng caching; kho nhỏ thì cân nhắc bỏ RAG.

Kiểm tra nhanh

Với λ = 1, MMR hoạt động thế nào? Với λ = 0?

λ = 1: chỉ xét độ liên quan — giống top-k thông thường. λ = 0: chỉ xét sự khác biệt — chọn đoạn khác nhau nhất bất kể liên quan hay không. Giá trị 0,5–0,8 thường hợp lý.

Prompt bắt đầu bằng "Hôm nay là 12/10/2026 14:03:27". Ảnh hưởng gì tới caching?

Phần đầu prompt thay đổi mỗi giây nên cache không bao giờ khớp. Đưa thông tin thời gian xuống sau phần ổn định (hoặc chỉ ghi ngày, không ghi giờ).

Kho tài liệu 120 trang, cập nhật mỗi quý, mọi nhân viên đều được xem. RAG hay long-context?

Long-context + prompt caching đáng thử trước: kho nhỏ (ước chừng vài chục nghìn token), ít thay đổi, không cần phân quyền. Đơn giản hơn nhiều so với vận hành pipeline RAG.
