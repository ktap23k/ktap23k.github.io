Lab: xây bộ đánh giá và vòng lặp cải tiến

Bài Lab quan trọng nhất của khoá học. Sau bài này, mọi thay đổi trong pipeline — đổi chunk size, thêm reranker, sửa prompt — đều đi kèm một con số trả lời câu hỏi "có tốt hơn không?".

Mục tiêu bài học

  • Xây golden set đa dạng từ câu hỏi thật và câu hỏi sinh tự động.
  • Viết script đánh giá retrieval và faithfulness.
  • Thiết lập vòng lặp: đo → phân tích lỗi → sửa một thứ → đo lại.

1. Golden set

Mỗi dòng trong golden.jsonl là một câu hỏi kèm đáp án và id các chunk chứa thông tin cần thiết:

{"id": "q017", "type": "factoid", "question": "Nhân viên thử việc có được nghỉ phép năm không?",
 "answer": "Có, được tính theo số tháng làm việc thực tế.", "relevant_ids": ["hr/nghi-phep.md#2"]}
{"id": "q031", "type": "unanswerable", "question": "Công ty có hỗ trợ gửi xe ô tô không?",
 "answer": null, "relevant_ids": []}

Bắt đầu với 50–100 câu, phủ đủ các loại: factoid (một chi tiết), multi_hop (cần hai tài liệu), unanswerable (không có trong tài liệu), no_diacritics (gõ không dấu), conversational (phụ thuộc câu trước). Nguồn câu hỏi tốt nhất là log câu hỏi thật của người dùng.

Sinh câu hỏi tự động

GEN_PROMPT = """Đọc đoạn tài liệu sau và viết 2 câu hỏi mà một nhân viên thực sự có thể hỏi,
được trả lời bởi đoạn này. Dùng từ ngữ đời thường, KHÁC cách diễn đạt trong tài liệu.
Trả về JSON: [{{"question": "...", "answer": "..."}}]

Tài liệu ({chunk_id}):
{text}"""
Câu hỏi sinh tự động dễ "dễ quá"

LLM có xu hướng chép lại từ ngữ của tài liệu, làm câu hỏi khớp từ khoá một cách giả tạo và thổi phồng điểm. Luôn đọc lại, loại câu kém, và trộn với câu hỏi thật.

2. Đánh giá retrieval

# eval_retrieval.py
import json
import math

def recall_at_k(retrieved: list[str], relevant: set[str], k: int) -> float:
    return len(set(retrieved[:k]) & relevant) / len(relevant)

def reciprocal_rank(retrieved: list[str], relevant: set[str]) -> float:
    return next((1 / rank for rank, cid in enumerate(retrieved, 1) if cid in relevant), 0.0)

def ndcg_at_k(retrieved: list[str], relevant: set[str], k: int) -> float:
    dcg = sum(1 / math.log2(i + 2) for i, cid in enumerate(retrieved[:k]) if cid in relevant)
    ideal = sum(1 / math.log2(i + 2) for i in range(min(len(relevant), k)))
    return dcg / ideal

def evaluate(search, golden_path: str, k: int = 5) -> dict[str, float]:
    """search(question, k) trả về danh sách chunk_id theo thứ hạng."""
    with open(golden_path, encoding="utf-8") as f:
        items = [json.loads(line) for line in f if line.strip()]
    rows = []
    for item in items:
        relevant = set(item["relevant_ids"])
        if not relevant:                       # câu không có đáp án: đánh giá ở bước generation
            continue
        retrieved = search(item["question"], k=50)
        rows.append((recall_at_k(retrieved, relevant, k), reciprocal_rank(retrieved, relevant),
                     ndcg_at_k(retrieved, relevant, k), recall_at_k(retrieved, relevant, 50)))
    names = [f"recall@{k}", "mrr", f"ndcg@{k}", "recall@50"]
    return {name: round(sum(col) / len(rows), 3) for name, col in zip(names, zip(*rows))}

3. Chấm faithfulness bằng LLM

JUDGE_PROMPT = """Bạn là giám khảo nghiêm khắc. Tách CÂU TRẢ LỜI thành các khẳng định riêng lẻ.
Với mỗi khẳng định, xét xem NGỮ CẢNH có hỗ trợ trực tiếp không.
Trả về JSON: {{"claims": [{{"claim": "...", "supported": true}}]}}

NGỮ CẢNH:
{context}

CÂU TRẢ LỜI:
{answer}"""

def faithfulness(context: str, answer: str) -> float | None:
    claims = json.loads(call_llm(JUDGE_PROMPT.format(context=context, answer=answer)))["claims"]
    if not claims:                             # ví dụ câu từ chối: không có khẳng định nào
        return None
    return sum(c["supported"] for c in claims) / len(claims)

Với câu unanswerable, chỉ cần kiểm tra câu trả lời có chứa câu từ chối chuẩn hay không. Ghi riêng hai tỉ lệ: từ chối đúng (trên câu không có đáp án) và từ chối nhầm (trên câu có đáp án).

4. Kiểm thử hồi quy trong CI

# test_rag_quality.py — chạy bằng pytest khi đổi prompt, model, chunking...
from eval_retrieval import evaluate
from app.search import search_ids

def test_retrieval_does_not_regress():
    metrics = evaluate(search_ids, "eval/golden.jsonl", k=5)
    assert metrics["recall@5"] >= 0.80, metrics
    assert metrics["mrr"] >= 0.60, metrics

Ngưỡng lấy từ lần đo tốt nhất hiện tại trừ một khoảng nhỏ cho dao động. Phần retrieval không gọi LLM nên chạy nhanh, rẻ, tất định — rất hợp để chặn trong CI. Phần chấm bằng LLM có thể chạy hằng đêm.

5. Vòng lặp cải tiến

  1. Đo baseline
  2. Đọc 20 câu sai
  3. Phân loại lỗi
  4. Sửa một thứ
  5. Đo lại, ghi nhật ký

Ghi mỗi thí nghiệm vào một bảng nhật ký: cấu hình, Recall@5, MRR, faithfulness, p95 latency, chi phí/1.000 câu. Ví dụ minh hoạ về hình dạng của nhật ký (không phải số liệu đo thật):

Thí nghiệmRecall@5MRRp95Kết luận
Baseline: vector, chunk 800 ký tự0,620,480,9 s—
+ chunk theo heading0,680,530,9 sGiữ

Tóm tắt

  • Golden set 50–100 câu đa dạng, ưu tiên câu hỏi thật; câu sinh tự động phải được duyệt.
  • Metric retrieval rẻ và tất định → chặn hồi quy trong CI.
  • Faithfulness chấm bằng LLM theo từng khẳng định; theo dõi riêng tỉ lệ từ chối.
  • Mỗi lần chỉ đổi một thứ, ghi nhật ký thí nghiệm, giữ lại thứ cải thiện số đo.

Kiểm tra nhanh

Vì sao script tính thêm Recall@50 bên cạnh Recall@5?

Để phân biệt "không tìm thấy" (Recall@50 thấp → sửa retrieval) với "tìm thấy nhưng xếp hạng kém" (Recall@50 cao, Recall@5 thấp → thêm/chỉnh reranker).

Đổi đồng thời chunk size và embedding model, Recall tăng 5%. Vấn đề là gì?

Không biết thay đổi nào tạo ra cải thiện (có thể một cái tốt, một cái xấu). Chỉ đổi một biến mỗi thí nghiệm.

Golden set toàn câu hỏi sinh tự động cho Recall@5 = 0,97 nhưng người dùng thật phàn nàn nhiều. Vì sao?

Câu hỏi sinh tự động thường dùng lại từ ngữ của tài liệu nên khớp dễ; câu hỏi thật ngắn, mơ hồ, sai chính tả, không dấu. Cần bổ sung câu hỏi từ log thật.
