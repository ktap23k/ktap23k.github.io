Vector database và chỉ mục ANN

So câu hỏi với từng vector một (như bài Lab) ổn với vài chục nghìn chunk. Với hàng chục triệu, ta cần chỉ mục gần đúng: hy sinh một chút độ chính xác để nhanh hơn hàng trăm lần.

Mục tiêu bài học

  • Hiểu cách HNSW và IVF tăng tốc tìm kiếm, cùng các tham số cần chỉnh.
  • Ước lượng bộ nhớ và biết khi nào dùng quantization.
  • Chọn vector database phù hợp và lọc metadata đúng cách.

Tìm chính xác và tìm gần đúng

Tìm chính xác (flat/brute-force) có độ phức tạp O(N·d) cho mỗi truy vấn. Các thuật toán ANN (Approximate Nearest Neighbor) chỉ xét một phần nhỏ dữ liệu, đổi lại có thể bỏ sót vài láng giềng thật. Thước đo chất lượng của ANN là recall so với tìm chính xác — thường đặt mục tiêu 0,95–0,99.

HNSW — đồ thị nhiều tầng

HNSW (Malkov & Yashunin) xây đồ thị trong đó mỗi vector nối với vài láng giềng gần; các tầng trên thưa như "đường cao tốc", tầng dưới dày như "đường nội đô". Tìm kiếm bắt đầu từ tầng trên cùng rồi đi dần xuống. Đây là chỉ mục mặc định của phần lớn vector database.

  • M: số cạnh mỗi nút (thường 16–32). Lớn hơn → recall cao hơn, tốn RAM hơn.
  • ef_construction: độ kỹ khi xây (64–200). Lớn hơn → index chậm hơn, chất lượng tốt hơn.
  • ef_search: độ rộng khi tìm — núm vặn chính giữa tốc độ và recall, chỉnh được lúc chạy.

IVF — chia cụm

Gom vector thành nlist cụm bằng k-means; lúc tìm chỉ quét nprobe cụm gần câu hỏi nhất. Tốn ít RAM hơn HNSW, xây nhanh, nhưng phải train lại cụm khi phân bố dữ liệu thay đổi nhiều.

Ước lượng bộ nhớ và quantization

Vector float32 tốn 4 byte mỗi chiều: 1 triệu chunk × 1024 chiều × 4 byte ≈ 4 GB, chưa kể overhead của đồ thị HNSW. Ba cách giảm:

  • Giảm số chiều với model hỗ trợ Matryoshka (ví dụ 1024 → 512).
  • Scalar quantization (int8): nhỏ hơn 4 lần, giảm chất lượng rất ít.
  • Binary quantization: nhỏ hơn 32 lần; dùng để lọc ứng viên nhanh rồi rescore bằng vector gốc.

Lời khuyên thực dụng

Nếu team đã chạy PostgreSQL, hãy bắt đầu với pgvector. Một hệ thống ít thành phần dễ vận hành hơn nhiều; chỉ chuyển sang vector database chuyên dụng khi số đo cho thấy cần.

Ví dụ với pgvector

CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
  id          bigserial PRIMARY KEY,
  doc_id      text   NOT NULL,
  content     text   NOT NULL,
  metadata    jsonb  NOT NULL DEFAULT '{}',
  embedding   vector(1024) NOT NULL
);

CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
CREATE INDEX ON chunks USING gin (metadata jsonb_path_ops);

-- 5 chunk gần nhất trong các tài liệu người dùng được phép xem
SET hnsw.ef_search = 100;
SELECT id, content, 1 - (embedding <=> $1) AS similarity
FROM chunks
WHERE metadata @> '{"department": "hr"}'
ORDER BY embedding <=> $1
LIMIT 5;

Toán tử <=> là khoảng cách cosine (<-> là L2, <#> là tích vô hướng âm). Index HNSW chỉ được dùng khi ORDER BY đúng toán tử tương ứng với opclass.

Bẫy khi lọc metadata

Với chỉ mục ANN, có hai cách kết hợp lọc và tìm:

  • Post-filter: tìm top-k trước rồi lọc. Nếu bộ lọc chặt (chỉ 1% tài liệu thoả mãn), kết quả có thể còn 0–1 chunk dù dữ liệu phù hợp vẫn tồn tại.
  • Pre-filter / lọc trong lúc duyệt: đúng hơn, nhưng cần database hỗ trợ tốt. Qdrant, Milvus, Weaviate lọc trong quá trình duyệt đồ thị; pgvector từ bản 0.8 có iterative index scan (SET hnsw.iterative_scan = relaxed_order) để quét tiếp khi lọc làm thiếu kết quả.

Với phân quyền nhiều tenant, cân nhắc tách collection/partition theo tenant thay vì lọc trên một chỉ mục chung.

Tóm tắt

  • ANN đổi một chút recall lấy tốc độ; HNSW là mặc định, ef_search là núm vặn chính.
  • Ước lượng RAM: số vector × số chiều × 4 byte (+ overhead); giảm bằng Matryoshka hoặc quantization.
  • Đã có Postgres → bắt đầu với pgvector.
  • Lọc metadata chặt có thể làm thiếu kết quả nếu database chỉ post-filter.

Kiểm tra nhanh

5 triệu chunk, 768 chiều, float32 cần khoảng bao nhiêu RAM cho riêng vector?

5.000.000 × 768 × 4 byte ≈ 15,4 GB (chưa tính overhead đồ thị). Với int8 quantization còn khoảng 3,8 GB.

Người dùng phòng "legal" (2% tài liệu) luôn nhận kết quả rất ít dù có nhiều tài liệu phù hợp. Nguyên nhân khả dĩ?

Post-filtering: ANN lấy top-k trên toàn bộ kho, phần lớn thuộc phòng khác và bị lọc bỏ. Cần lọc trong lúc duyệt (filterable HNSW, iterative scan) hoặc tách partition theo phòng ban.

Recall đo trên ANN chỉ đạt 0,85. Chỉnh gì trước?

Tăng ef_search (không cần xây lại index). Nếu vẫn thấp, xây lại với M hoặc ef_construction lớn hơn.
